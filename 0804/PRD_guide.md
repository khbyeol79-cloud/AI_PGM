# PRD 설명과 작성 가이드

## 1. PRD란?

PRD는 **Product Requirements Document**의 약자로, 우리말로는 보통 **제품 요구사항 정의서**라고 합니다.

만들려는 제품이나 서비스가 다음 질문에 답하도록 정리한 문서입니다.

- 왜 이 제품을 만드는가?
- 누구를 위한 제품인가?
- 어떤 문제를 해결하는가?
- 어떤 기능이 필요한가?
- 어떤 기준을 만족하면 완성되었다고 판단하는가?

PRD는 기획자만 보는 문서가 아니라 개발자, 디자이너, 테스터, 프로젝트 관리자 등 제품 제작에 참여하는 사람들이 같은 목표를 이해하도록 돕는 기준 문서입니다.

---

## 2. PRD가 필요한 이유

### 2.1 목표를 명확하게 한다

제품을 만드는 이유와 해결할 문제를 문서화하여 불필요한 기능 개발을 줄입니다.

### 2.2 팀의 이해를 통일한다

기획자, 개발자, 디자이너가 서로 다르게 이해하는 상황을 방지합니다.

### 2.3 개발 범위를 관리한다

반드시 필요한 기능과 나중에 추가할 기능을 구분하여 일정과 비용을 관리할 수 있습니다.

### 2.4 테스트 기준을 제공한다

기능이 정상적으로 완성되었는지 판단할 수 있는 명확한 기준을 제공합니다.

### 2.5 의사결정 기록을 남긴다

어떤 기능을 왜 포함하거나 제외했는지 기록하여 이후 변경이나 유지보수에 활용할 수 있습니다.

---

## 3. PRD의 핵심 구성요소

### 3.1 문서 기본 정보

- 제품명 또는 프로젝트명
- 문서 작성자
- 작성일 및 수정일
- 문서 버전
- 프로젝트 상태

### 3.2 제품 개요

제품이 무엇인지 짧고 명확하게 설명합니다.

**예시**

> 개인이 보유한 책을 등록하고 대여 상태와 독서 기록을 관리할 수 있는 웹 기반 도서 관리 프로그램을 개발한다.

### 3.3 배경과 문제 정의

사용자가 현재 겪고 있는 문제와 제품이 필요한 이유를 작성합니다.

**예시**

> 보유한 책이 많아지면 어떤 책을 가지고 있는지 확인하기 어렵고, 다른 사람에게 빌려준 책의 상태를 잊기 쉽다.

좋은 문제 정의는 해결 방법보다 먼저 **사용자의 불편과 원인**을 설명합니다.

### 3.4 제품 목표

제품을 통해 달성하려는 결과를 작성합니다. 가능하면 측정할 수 있는 형태가 좋습니다.

**예시**

- 사용자가 1분 이내에 책 한 권을 등록할 수 있다.
- 제목이나 저자명으로 원하는 책을 3초 이내에 찾을 수 있다.
- 대여 중인 책과 반납 예정일을 한 화면에서 확인할 수 있다.

### 3.5 목표가 아닌 것

이번 개발 범위에 포함하지 않을 내용을 명시합니다. 이를 보통 `Non-goals`라고 합니다.

**예시**

- 초기 버전에서는 전자책 파일을 직접 열람하는 기능을 제공하지 않는다.
- 온라인 서점 결제 기능은 포함하지 않는다.
- 여러 기관이 사용하는 대규모 도서관 시스템은 목표로 하지 않는다.

### 3.6 대상 사용자

제품을 사용할 사람과 사용 환경을 정의합니다.

**예시**

- 개인 도서 보유자
- 소규모 독서 모임 운영자
- 집과 외부에서 스마트폰 또는 PC로 책 목록을 확인하려는 사용자

### 3.7 사용자 시나리오 또는 사용자 스토리

사용자가 어떤 목적으로 기능을 이용하는지 작성합니다.

일반적인 사용자 스토리 형식은 다음과 같습니다.

> 나는 `[사용자 유형]`으로서, `[목적]`을 위해 `[기능]`을 원한다.

**예시**

- 나는 개인 사용자로서 보유 도서를 확인하기 위해 책을 등록하고 싶다.
- 나는 독서 모임 운영자로서 빌려준 책을 관리하기 위해 대여자와 반납 예정일을 기록하고 싶다.
- 나는 외부에 있는 사용자로서 중복 구매를 피하기 위해 스마트폰으로 책을 검색하고 싶다.

### 3.8 기능 요구사항

제품이 반드시 제공해야 하는 기능을 구체적으로 작성합니다.

| ID | 기능 | 요구사항 | 우선순위 |
|---|---|---|---|
| FR-01 | 회원가입·로그인 | 사용자는 이메일과 비밀번호로 계정을 만들고 로그인할 수 있다. | 필수 |
| FR-02 | 도서 등록 | 사용자는 제목, 저자, 출판사, ISBN을 입력하여 책을 등록할 수 있다. | 필수 |
| FR-03 | 도서 검색 | 사용자는 제목, 저자 또는 ISBN으로 등록된 책을 검색할 수 있다. | 필수 |
| FR-04 | 대여 관리 | 사용자는 대여자, 대여일, 반납 예정일을 기록할 수 있다. | 필수 |
| FR-05 | 독서 기록 | 사용자는 독서 상태와 감상문을 기록할 수 있다. | 선택 |

요구사항에는 `적당히`, `빠르게`, `편리하게`처럼 판단 기준이 불분명한 표현보다 확인 가능한 조건을 사용합니다.

### 3.9 비기능 요구사항

기능 자체가 아니라 성능, 보안, 안정성, 사용성 등 제품의 품질 조건을 작성합니다.

| 구분 | 요구사항 예시 |
|---|---|
| 성능 | 일반적인 검색 결과는 3초 이내에 표시한다. |
| 보안 | 비밀번호는 원문으로 저장하지 않고 안전한 방식으로 암호화한다. |
| 반응형 | 스마트폰, 태블릿, PC 화면에서 사용할 수 있어야 한다. |
| 백업 | 데이터는 정기적으로 백업할 수 있어야 한다. |
| 안정성 | 저장 도중 오류가 발생해도 기존 데이터가 손상되지 않아야 한다. |

### 3.10 우선순위

모든 기능을 한 번에 만들기 어려우므로 중요도를 구분합니다.

MoSCoW 방식의 예시는 다음과 같습니다.

- **Must have:** 반드시 필요한 기능
- **Should have:** 중요하지만 일정에 따라 조정 가능한 기능
- **Could have:** 여유가 있으면 포함할 기능
- **Won't have:** 이번 버전에는 포함하지 않을 기능

### 3.11 화면 및 사용자 흐름

사용자가 기능을 이용하는 순서를 정리합니다.

**예시**

1. 사용자가 로그인한다.
2. 도서 등록 화면을 연다.
3. 책 정보를 입력하고 저장한다.
4. 시스템이 입력값을 확인한다.
5. 저장에 성공하면 도서 목록에 새 책을 표시한다.

필요하면 화면 설계서, 와이어프레임 또는 디자인 파일의 링크를 함께 기록합니다.

### 3.12 데이터 요구사항

저장해야 하는 데이터와 주요 관계를 작성합니다.

**도서 정보 예시**

- 도서 고유번호
- 제목
- 저자
- 출판사
- ISBN
- 보유 상태
- 등록일

**대여 정보 예시**

- 대여 기록 고유번호
- 도서 고유번호
- 대여자
- 대여일
- 반납 예정일
- 실제 반납일

### 3.13 완료 조건과 인수 기준

기능이 완성되었다고 판단할 수 있는 조건을 작성합니다. 이를 `Acceptance Criteria`라고 합니다.

**도서 등록 기능의 인수 기준 예시**

- 제목과 저자를 입력하면 책이 정상적으로 저장된다.
- 필수 항목이 비어 있으면 저장되지 않고 안내 문구가 표시된다.
- 이미 등록된 ISBN을 입력하면 중복 여부를 사용자에게 알린다.
- 저장된 책은 즉시 도서 목록과 검색 결과에 나타난다.
- 페이지를 새로 열어도 저장한 정보가 유지된다.

### 3.14 성공 지표

제품이 실제로 목표를 달성했는지 확인할 지표를 정합니다.

**예시**

- 도서 등록 성공률 95% 이상
- 검색 결과 표시 시간 평균 3초 이하
- 회원가입 후 첫 도서 등록 완료율 70% 이상
- 한 달 동안 실제로 사용하는 사용자 비율

### 3.15 일정과 단계

주요 개발 단계를 작성합니다.

| 단계 | 주요 내용 |
|---|---|
| 1단계 | 요구사항 확정 및 화면 설계 |
| 2단계 | 회원, 도서 등록, 검색 기능 개발 |
| 3단계 | 대여 관리 및 독서 기록 기능 개발 |
| 4단계 | 테스트와 오류 수정 |
| 5단계 | 배포 및 사용자 피드백 수집 |

### 3.16 위험 요소와 미정 사항

결정되지 않은 내용이나 개발에 영향을 줄 수 있는 요소를 기록합니다.

**예시**

- ISBN을 이용한 외부 도서 정보 검색 API를 어떤 것으로 선택할 것인가?
- 인터넷이 연결되지 않은 환경에서도 사용할 것인가?
- 개인 서버에 설치할 때 백업과 외부 접속 방식을 어떻게 구성할 것인가?
- 사용자 수와 저장 가능한 도서 수의 제한을 둘 것인가?

## 4. PRD 작성 순서

1. 해결할 문제를 한 문장으로 정의한다.
2. 대상 사용자를 정한다.
3. 제품의 목표와 제외 범위를 정한다.
4. 사용자가 제품을 사용하는 상황을 작성한다.
5. 필요한 기능을 목록으로 만든다.
6. 기능의 우선순위를 정한다.
7. 각 기능의 완료 조건을 작성한다.
8. 성능, 보안, 사용 환경 등 비기능 요구사항을 정한다.
9. 성공 지표와 일정을 정한다.
10. 팀 검토 후 변경 사항과 결정 내용을 지속적으로 갱신한다.

## 5. PRD와 다른 문서의 차이

| 문서 | 중심 질문 | 주요 내용 |
|---|---|---|
| PRD | 무엇을, 왜 만들어야 하는가? | 사용자 문제, 목표, 기능, 요구사항, 완료 조건 |
| 기획서 | 제품이나 사업을 어떻게 추진할 것인가? | 배경, 시장, 운영 계획, 기대 효과 등을 폭넓게 포함 |
| 화면 설계서 | 화면은 어떻게 구성되는가? | 메뉴, 버튼, 입력 항목, 화면 이동 |
| 기술 설계서 | 기술적으로 어떻게 구현할 것인가? | 시스템 구조, 데이터베이스, API, 기술 선택 |
| 테스트 계획서 | 무엇을 어떻게 검증할 것인가? | 테스트 범위, 방법, 예상 결과 |

PRD는 기술 구현 방법을 지나치게 자세히 설명하기보다 제품이 충족해야 할 요구사항에 집중합니다. 구체적인 서버 구조, 데이터베이스 설계, API 형식 등은 별도의 기술 설계서에서 다루는 것이 일반적입니다.

---

## 6. 좋은 PRD의 조건

- 제품이 해결하려는 문제가 명확하다.
- 사용자와 사용 상황이 구체적이다.
- 요구사항을 테스트할 수 있다.
- 기능의 우선순위와 제외 범위가 분명하다.
- 모호하거나 중복되는 표현이 적다.
- 변경된 요구사항과 결정 이유가 기록되어 있다.
- 개발자, 디자이너, 테스터가 같은 의미로 이해할 수 있다.

## 7. 자주 발생하는 실수

### 기능 목록만 작성하는 경우

기능을 만드는 이유와 사용자 문제가 없으면 우선순위를 판단하기 어렵습니다.

### 요구사항이 모호한 경우

`화면이 빨라야 한다`보다 `검색 결과가 3초 이내에 표시되어야 한다`처럼 작성합니다.

### 모든 기능을 필수로 지정하는 경우

최소 기능 제품(MVP)에 필요한 기능과 이후 버전에 추가할 기능을 구분해야 합니다.

### 구현 방법을 너무 일찍 확정하는 경우

제품 요구사항과 기술 구현 방식을 구분해야 더 적절한 기술적 대안을 검토할 수 있습니다.

### 작성 후 갱신하지 않는 경우

PRD는 한 번 작성하고 끝나는 문서가 아니라 프로젝트가 진행되면서 결정과 변경 내용을 반영하는 살아 있는 문서입니다.

## 9. 핵심 정리

PRD는 단순한 기능 목록이 아니라 **사용자의 문제, 제품의 목표, 필요한 기능, 완료 판단 기준을 하나로 연결하는 문서**입니다.

좋은 PRD는 다음 문장으로 요약할 수 있습니다.

> 누구의 어떤 문제를 해결하기 위해 무엇을 만들고, 어떤 조건을 만족하면 완성으로 볼 것인지 명확하게 기록한 문서
